# TAIMIO — подробное техническое задание MVP

Версия ТЗ: 0.1
Рабочее название: **TAIMIO**
Слоган: **«Не пересматривай. Найди.»**
Целевая платформа первой версии: **Windows desktop**

---

## 1. Идея продукта

TAIMIO — локально устанавливаемая настольная программа для работы с длинными видео и коллекциями видео. Пользователь загружает один или несколько видеофайлов, программа получает полную расшифровку с таймкодами, структурирует содержание, создаёт план и краткий конспект, позволяет искать нужную информацию обычным человеческим запросом и показывает точное место в исходном видео. Дополнительно TAIMIO должен извлекать важные визуальные материалы — графики, таблицы, схемы, слайды и другие информативные кадры.

Главная пользовательская ценность: вместо повторного просмотра многочасовых записей пользователь получает навигацию по знаниям внутри видео.

---

## 2. Формат приложения

Это НЕ публичный сайт и НЕ страница, которую пользователь вручную запускает через терминал.

Первая версия должна быть полноценным Windows desktop-приложением:
- привычный установщик;
- ярлык на рабочем столе и/или в меню «Пуск»;
- запуск двойным кликом;
- собственное окно приложения;
- конечному пользователю не нужны Cursor, Python, Node.js, терминал или IDE;
- необходимые runtime-компоненты должны поставляться с приложением либо устанавливаться через понятный мастер первого запуска;
- пользовательские проекты должны храниться отдельно от файлов установки программы;
- обновление/переустановка приложения не должна уничтожать проекты пользователя.

Cursor должен предложить подходящий стек desktop-разработки. Предпочтение — современному веб-интерфейсу внутри desktop-shell, но выбор технологии должен быть обоснован с учётом Python/FFmpeg/faster-whisper, упаковки Windows, размера приложения и удобства разработки MVP.

---

## 3. Первый запуск и главный экран

При запуске пользователь видит фирменный экран TAIMIO в стиле `design/taimio-welcome-screen.png`.

Основные действия:
- **Новый проект**;
- **Продолжить работу** / список существующих проектов.

Карточка существующего проекта должна показывать минимум:
- название;
- дату последнего открытия/изменения;
- количество видео;
- состояние обработки;
- выбранный режим AI.

При создании проекта пользователь задаёт название и выбирает способ обработки AI.

---

## 4. Два режима AI

Выбор режима относится к проекту, а не навсегда ко всей программе. В настройках проекта режим можно изменить с явным предупреждением о приватности.

### 4.1 Облачный режим

Понятное описание для пользователя: быстрее, проще и обычно позволяет использовать более сильную AI-модель, однако необходимые текстовые фрагменты могут передаваться внешнему AI-провайдеру.

MVP должен предусматривать OpenAI как первый облачный provider, но AI-слой архитектурно не должен быть жёстко связан с одним провайдером.

Пользователь:
- вводит собственный API-ключ;
- может проверить подключение;
- может заменить ключ;
- может удалить/очистить сохранённый ключ.

Требования безопасности:
- ключ не хранить в исходном коде;
- ключ не коммитить в Git;
- ключ не включать в установочный пакет;
- не писать полный ключ в логи;
- использовать безопасное локальное хранилище credentials, предпочтительно Windows Credential Manager/DPAPI или эквивалент;
- интерфейс показывает ключ маскированно.

Исходное видео и аудио по умолчанию не должны отправляться в облачную LLM. Облачному AI передаются только необходимые текстовые фрагменты/структурированные данные, если выбран соответствующий режим.

### 4.2 Полностью локальный режим

Все материалы и AI-анализ остаются на компьютере пользователя.

При выборе режима приложение запускает мастер готовности системы и показывает понятные статусы компонентов, например:
- FFmpeg;
- локальный модуль speech-to-text;
- локальная языковая модель/runtime;
- доступное место на диске;
- RAM и при необходимости GPU/VRAM.

Где технически и лицензионно возможно, дать кнопку **«Установить всё необходимое»** и автоматизировать установку/загрузку из официальных источников. Если автоматическая установка компонента нецелесообразна, показать официальную ссылку и пошаговую инструкцию, после чего уметь повторно проверить наличие компонента.

Перед реализацией Cursor обязан проверить актуальные лицензии выбранных runtime, моделей и библиотек и указать ограничения на распространение.

### 4.3 Экран приватности

Пользователь должен ясно понимать поток данных.

Облачный режим примерно:
- видео — локально;
- аудио — локально;
- скриншоты — локально;
- расшифровка — локально;
- необходимые текстовые фрагменты — могут передаваться AI-провайдеру;
- результаты — сохраняются локально.

Локальный режим: никакие материалы проекта не передаются внешним AI-сервисам.

---

## 5. Добавление видео

Внутри проекта пользователь может добавить одно или несколько видео.

Нужно предусмотреть:
- выбор файлов через диалог;
- drag & drop как желательное улучшение;
- список видео;
- название файла;
- длительность;
- размер;
- статус обработки;
- возможность переименовать отображаемое название видео без переименования оригинального файла;
- удаление видео из проекта только после подтверждения.

Исходные пользовательские файлы нельзя без явного согласия физически удалять с диска.

---

## 6. Pipeline обработки видео

Обработка должна быть этапной и возобновляемой.

Предполагаемый pipeline:
1. Регистрация исходного видео в проекте.
2. Получение метаданных.
3. Извлечение/подготовка аудио через FFmpeg.
4. Speech-to-text с таймкодами.
5. Нормализация транскрипта.
6. Разбиение на смысловые блоки.
7. Создание заголовка/главной мысли каждого блока.
8. Создание тезисного содержания блока.
9. Сбор плана видео.
10. Построение индекса для смыслового поиска.
11. Поиск кандидатов на визуальные материалы и извлечение кадров.
12. Сохранение результатов.

Каждый этап имеет состояние и сохранённый результат. Если программа закрылась или произошла ошибка, повторный запуск не должен пересчитывать уже успешно завершённые дорогие этапы без необходимости.

Нужны состояния наподобие: queued / processing / completed / failed / needs_retry.

Пользователь должен видеть человеческий прогресс: «Подготовка аудио», «Распознаём речь», «Создаём конспект», «Индексируем поиск», «Ищем визуальные материалы».

---

## 7. Распознавание речи

Для локального распознавания рассмотреть `faster-whisper`/Whisper-совместимую реализацию и FFmpeg. Перед фиксацией решения проверить актуальные лицензии и варианты упаковки.

Ключевое требование: результат должен содержать текст, связанный с таймкодами. По возможности хранить сегменты с start/end, а при доступности качественных word-level timestamps — предусмотреть их без обязательного использования в MVP.

Модель распознавания не обязательно включать внутрь установщика. Допустим предпочтительный UX: при первом использовании локальной транскрибации приложение предлагает загрузить подходящую модель один раз, показывает её размер и прогресс загрузки.

Необходимо предусмотреть выбор/автоопределение языка, минимум русский язык как основной сценарий MVP.

---

## 8. Полная расшифровка

Для каждого видео отдельная вкладка/экран полной расшифровки.

Функции:
- текст по временным сегментам;
- видимые таймкоды;
- клик по таймкоду открывает/перематывает видео на соответствующий момент;
- поиск по тексту;
- возможность ручного редактирования ошибок распознавания;
- сохранение правок;
- пометка, что после существенной правки конспект/индекс могут потребовать перестроения;
- команда **«Перестроить анализ по исправленной расшифровке»**.

---

## 9. Смысловые блоки, план и конспект

Не ориентироваться на случайные «абзацы» STT. Анализ должен делить содержание на смысловые блоки/темы.

Для каждого блока хранить:
- start time;
- end time;
- короткий заголовок — главная мысль;
- тезисное содержание;
- связь с исходными transcript segments.

### План видео
План — последовательность главных мыслей смысловых блоков с таймкодами.

### Краткое содержание
Для каждого пункта плана:
- заголовок/главная мысль;
- временной диапазон;
- несколько содержательных тезисов.

Не допускать выдумывания фактов, которых нет в транскрипте. Аналитические результаты должны быть привязаны к исходным сегментам.

---

## 10. Смысловой поиск

Это одна из ключевых функций продукта.

Пользователь вводит запрос естественным языком, например: «Где говорили про падение показателя после второго квартала?»

Если в проекте несколько видео, доступны фильтры:
- все видео;
- конкретное видео 1;
- конкретное видео 2 и т.д.

Поиск должен быть не только точным совпадением слов, но и смысловым.

Предпочтительная архитектура: локальный индекс по небольшим текстовым фрагментам с сохранёнными таймкодами; LLM, если она нужна для финального ответа/ранжирования, получает только небольшой набор релевантных кандидатов, а не весь многочасовой транскрипт.

Результат поиска показывает несколько совпадений:
- видео;
- точный/приближённый таймкод;
- короткий релевантный фрагмент/объяснение;
- степень релевантности или понятное ранжирование;
- кнопку **«Перейти к моменту»**.

Если возможно, встроенный видеоплеер должен открывать видео на найденном моменте.

---

## 11. Визуальные материалы

Отдельный модуль/вкладка **«Визуальные материалы»**.

Цель: автоматически находить и сохранять информативные кадры, связанные с содержанием видео:
- графики;
- диаграммы;
- таблицы;
- схемы;
- слайды;
- демонстрации документов/интерфейсов;
- другие значимые визуальные элементы.

Для MVP использовать разумный гибридный подход, не анализируя каждый кадр дорогой vision-моделью. Возможные сигналы кандидатов:
- фразы транскрипта «на графике», «на этом слайде», «посмотрите на таблицу», «на схеме» и т.п.;
- смены сцен;
- выбор кадров вокруг релевантного таймкода;
- простые локальные эвристики.

Для каждого сохранённого материала:
- thumbnail;
- видео;
- таймкод;
- короткое описание;
- переход к исходному моменту;
- возможность открыть изображение крупно.

Архитектура должна позволять позже подключить vision-анализ, но MVP не должен зависеть от постоянной дорогой покадровой обработки.

---

## 12. Экспорт

Минимум три варианта экспорта в `.docx`:
1. Полная расшифровка.
2. Конспект.
3. Полный отчёт.

Полный отчёт может включать:
- название проекта;
- название видео;
- длительность;
- план;
- краткое содержание по смысловым блокам;
- ключевые таймкоды;
- выбранные визуальные материалы с подписями (если технически разумно для MVP).

Экспорт должен использовать уже сохранённые результаты, не запускать повторный AI-анализ.

---

## 13. Несколько видео и общий проект

Проект — контейнер для нескольких связанных видео.

Первая версия обязательно должна поддерживать поиск по всем видео проекта.

Архитектурно сразу предусмотреть будущую функцию **«Сводный конспект проекта»**, объединяющую знания из нескольких видео с указанием источников и таймкодов. Реализация может быть отложена после базового MVP, если она существенно увеличивает объём первого этапа.

---

## 14. Хранение данных

Нужно предложить надёжную локальную структуру данных. Предпочтительно использовать локальную БД (например SQLite) для метаданных/индексов и файловую структуру для крупных артефактов.

У каждого проекта должны сохраняться:
- project id;
- название;
- режим AI;
- ссылки/пути на исходные видео;
- метаданные видео;
- transcript segments и таймкоды;
- пользовательские исправления;
- смысловые блоки;
- план;
- конспект;
- поисковый индекс/embeddings;
- визуальные материалы;
- статусы pipeline;
- ошибки и информация для retry;
- версии/признаки устаревания производных данных после редактирования транскрипта.

Не дублировать многогигабайтные исходные видео без необходимости. Перед выбором стратегии копирования/ссылок объяснить компромисс: что произойдёт, если пользователь переместит исходный файл.

---

## 15. Исходники, кэш и удаление

Чётко разделить:
- пользовательские исходники;
- данные проекта;
- временные/служебные файлы;
- кэш моделей;
- экспортированные документы.

**«Очистить кэш» никогда не должна удалять исходные пользовательские видео.**

При удалении проекта показать, что именно будет удалено. Если исходное видео находится вне управляемой папки TAIMIO, не удалять его с диска по умолчанию.

---

## 16. UX ошибок и долгих операций

Длинные видео могут обрабатываться долго.

Нужно:
- прогресс;
- понятный текущий этап;
- отмена операции там, где безопасно;
- retry после ошибки;
- сохранение уже выполненных этапов;
- сообщения без технического жаргона;
- отдельный технический лог для диагностики, без секретов/API-ключей.

При нехватке места, памяти, отсутствии модели или FFmpeg пользователь получает конкретное объяснение и действие для исправления.

## 17. Визуальный стиль

Утверждённые референсы лежат в `/design`.

### Фирменная идея
Тёмный современный desktop-интерфейс: глубокий navy/graphite, мягкое неоновое свечение, фиолетово-синие и cyan-акценты, визуальная метафора таймлайна/времени/поиска нужной точки.

### Логотип
`design/taimio-logo.png` — утверждённое направление логотипа. Знак строится вокруг буквы T и таймлайна с выделенной точкой — «найденный момент во времени».

### Welcome screen
`design/taimio-welcome-screen.png` — утверждённое направление стартового экрана: TAIMIO, слоган, Новый проект, Открыть проект, основные возможности.

### Workspace
`design/taimio-workspace-background.png` — референс общей атмосферы рабочей области. Это не означает, что весь интерфейс должен быть одной фоновой картинкой. Реальный UI должен состоять из доступных компонентов поверх адаптированного фирменного фона/градиентов.

### Принципы
- не перегружать свечение;
- сохранять высокий контраст текста;
- поддерживать 100–200% Windows scaling;
- интерфейс должен нормально работать на распространённых разрешениях;
- фирменные картинки — референсы, а не замена реальным интерактивным элементам;
- русский язык — основной язык интерфейса MVP;
- предусмотреть архитектуру локализации на будущее.

## 20. Что НЕ нужно раздувать в первом MVP

Не делать сейчас без отдельного согласования:
- аккаунты пользователей;
- собственный сервер TAIMIO;
- облачную синхронизацию проектов;
- совместную работу;
- мобильное приложение;
- социальные функции;
- биллинг/подписку;
- автоматическую генерацию презентаций;
- тяжёлый vision-анализ каждого кадра;
- сложную систему автообновлений, если она тормозит первый рабочий build.

Сначала должен появиться устойчивый локальный продукт.

## 21. Критерии готовности MVP

MVP считается функционально состоявшимся, когда на чистом пользовательском Windows-компьютере после нормальной установки можно:
1. Запустить TAIMIO ярлыком без IDE/терминала.
2. Создать проект.
3. Выбрать облачный или локальный режим (локальный режим может требовать установки компонентов через мастер).
4. Добавить минимум одно длинное видео; архитектура поддерживает несколько.
5. Получить локально сохранённую расшифровку с таймкодами.
6. Получить план и краткий структурированный конспект.
7. Найти смысловым запросом нужный фрагмент и перейти к соответствующему таймкоду.
8. Увидеть найденные визуальные материалы/кадры.
9. Экспортировать расшифровку и конспект в Word.
10. Закрыть приложение, открыть снова и продолжить работу без повторной полной обработки.
11. После сбоя повторить только незавершённый этап.
12. Безопасно заменить или удалить API-ключ.

## 22. Предварительное разбиение разработки

Cursor должен после изучения ТЗ предложить своё разбиение, но ориентир такой:

**Этап 1. Каркас desktop-приложения** — проект, окно, навигация, дизайн-система, создание/открытие проектов, локальная БД.

**Этап 2. Видео и локальный pipeline** — импорт, метаданные, плеер, FFmpeg, статусы задач, возобновление.

**Этап 3. Транскрибация** — faster-whisper/выбранный STT, модель, таймкоды, экран расшифровки, редактирование.

**Этап 4. Cloud AI** — безопасный API-key UX, provider abstraction, смысловые блоки, план, конспект.

**Этап 5. Поиск** — chunking, индекс, embeddings/семантический retrieval, результаты с таймкодами.

**Этап 6. Визуальные материалы** — candidate detection, скриншоты, галерея, переход к моменту.

**Этап 7. Экспорт** — DOCX и полный отчёт.

**Этап 8. Полностью локальный AI** — мастер компонентов, локальный provider, hardware checks.

**Этап 9. Упаковка Windows** — production build, installer, ярлык, тест на чистой машине.

На каждом этапе сначала минимально рабочий вертикальный результат, затем тестирование. Не реализовывать следующие этапы без согласования пользователя.

## 23. Технические принципы

- Модульная архитектура.
- UI не должен знать детали конкретного AI-провайдера.
- Speech-to-text, AI analysis, search/indexing, export и storage — отдельные сервисные слои.
- Все дорогие операции должны быть идемпотентными/кэшируемыми там, где возможно.
- Результаты версионировать или помечать stale после изменения исходной расшифровки.
- Не загружать целый многочасовой транскрипт в LLM для каждого вопроса.
- Логи не содержат секретов.
- Ошибки внешнего API не должны повреждать локальный проект.
- Все сетевые действия должны быть явными и соответствовать выбранному режиму приватности.

## 24. Что Cursor должен сделать ДО написания кода

После полного чтения пакета Cursor должен:
1. Кратко пересказать назначение продукта.
2. Предложить конкретный стек и объяснить выбор.
3. Нарисовать текстовую архитектуру модулей.
4. Описать структуру локальных данных.
5. Объяснить упаковку Windows desktop и installer.
6. Объяснить cloud/local provider abstraction.
7. Указать внешние зависимости, размеры/лицензионные риски и то, что будет скачиваться пользователем.
8. Указать риски длинных видео, памяти, диска и восстановления.
9. Предложить окончательный план этапов.
10. Перечислить все файлы и изображения стартового пакета, которые были прочитаны.

После этого Cursor обязан остановиться и дождаться фразы пользователя: **«Принимаю план. Начинай этап 1»**.
